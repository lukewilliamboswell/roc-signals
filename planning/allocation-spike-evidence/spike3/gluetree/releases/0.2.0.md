# 0.2.0

## Migration: 0.1.1 → 0.2.0

This upgrade changes how applications run effects, build keyed lists, and
handle events. Upgrade the Roc compiler, the platform URL, and the browser
runtime together. Use Roc `nightly-2026-10-23-18478ff`, as recorded in every
example header and in `signals-release.json`; a recent but different nightly is
not a compatibility guarantee. The 0.2.0 release candidates are superseded and
need no separate migration.

### Effects are actions; tasks are gone

Event handlers, change observers, mounts, and timers now produce an `Action`.
An action is data the engine interprets: `Action.update` applies a batch of
state writes, and `Action.then` applies a batch and then runs effectful Roc
code whose result is the next action. Declared reads are snapshotted when the
event fires and again, freshly, before each effect. Import `pf.Action`.

The task model has been removed. `Signal.from_task`, `Signal.fold_task`,
`Signal.fake_task`, `Signal.task_source`, `Signal.task_source_with_eq`,
`Signal.start_str`, `Signal.done`, `Signal.failed`, `Signal.loading`, and the
`Http` task helpers (`Http.get`, `Http.get_text`, `Http.request`,
`Http.request_task`, `Http.get_text_task`, `Http.start`) no longer exist. Keep
a request's result in `Ui.state` and start it from an action:

- `Action.on_change_initial` with `Action.sampled` for a request driven by a
  signal, such as a route or search query;
- `Action.on_mount` for one-shot work;
- `Action.every` for polling;
- `Action.run` and its `run_str`, `run_bool`, `run_detail`, and `run_key`
  variants for an event handler that reads signals.

`Http.send!`, `Http.get!`, and `Http.get_text!` are effectful calls made inside
`Action.then`. They return `Try(_, Http.Error)`, which replaces `HttpError`:
match `InvalidRequest(Str)`, `Network(Str)`, `Timeout`, `TooLarge(Str)`,
`Status(U16)`, `InvalidUtf8`, and `Unavailable(Str)`. Effects admitted before a
scope is disposed still run, and their writes to disposed state are skipped.
Rejecting an obsolete response is application policy;
`examples-web/package-explorer` keeps a generation beside each result for this.
Native specs script HTTP answers and can hold effects with `manual-effects`.

### Event handlers

Handlers are now `Node.Handler` rather than `Node.Msg`. On `Ui.State`, rename
`on_unit` → `update`, `on_str` → `update_str`, `on_bool` → `update_bool`,
`on_detail` → `update_detail`, and `on_key` → `update_key`. The `*_with`
variants (`update_with`, `update_str_with`, and so on) also read a second
state. `state.set(value)` and `state.write(f)` build state writes for
`Action.update` or `Ui.update_states`, which replace several states in one
propagation turn so that derived values and observers see only the settled
result.

### Keyed lists

Replace `Ui.each_str(items, key_of, row)` with `Ui.each(rows, row)`. The
collection now owns and validates its key function:

```roc
import pf.Rows

rows = Rows.from_list(items, |item| item.id)?
```

Handle the `Try` where the collection is constructed. Duplicate keys, missing
keys, and invalid edit ranges are structured errors, not aliases or silent
fallbacks. For a static list, pass `Signal.const(rows)` to `Ui.each`; for a
changing collection, retain `Rows` in state and edit it with `Rows.apply`, or
use `Rows.replace_all` when a complete replacement is the input you have.

The row callback receives one live `Ui.Row(item)`. Use `row.key()` for identity
and `row.signal()` or `row.map(...)` for changing content; do not encode labels
or serialized items in the key. A same-key update preserves the row's scope,
removal ends it, and reintroducing a key after a committed removal creates fresh
local state. `Signal.select` and `Signal.keyed` express "is this row selected"
so that a selection change dirties only the old and new rows.

### Lazy branches

`Ui.when` invokes only the selected builder; code in an inactive builder no
longer runs eagerly. Use `Ui.switch(case_signal, build)` for more than two
cases. A case change disposes the old branch, including its local state; keep
persistent drafts outside the branch.

### Imports and new modules

The platform now exposes `Elem`, `Event`, `Action`, `Signal`, `Html`, `Svg`,
`Ui`, `Http`, `Browser`, and `Rows`. The `Elem` module is the type: replace
`import pf.Elem exposing [Elem]` with `import pf.Elem`, and annotations keep
writing `Elem`. `Svg` builds SVG elements that share ordinary attributes,
events, signals, and scopes. `Browser.entropy_seed` supplies a per-mount seed,
stable under native specs, for a pure PRNG; it is not for secrets.
`Signal.combine_map` combines and projects in one graph node.

### Browser deployment

The browser protocol is now version 17 (0.1.1 used 11). Rebuild the
application's Wasm and replace the runtime modules (`signals.mjs`,
`wasm_memory_views.mjs`, and `controlled_input_policy.mjs`) from this release's
`signals-examples.zip`, where they are under `browser/`. The runtime checks the
module's protocol version at mount and refuses a mismatch. Commands that fail
after a DOM event now contain the mount: listeners and behaviours detach,
later dispatch is rejected, and recovery requires a fresh mount.

Build Wasm applications with `--opt=size`. The pinned compiler's wasm32 dev
backend never re-selects a `Ui.when` branch it has left
([roc-lang/roc#12560](https://github.com/roc-lang/roc/issues/12560)); native
builds and `roc test` are unaffected.

## The GUI platform lives in roc-gui

The native desktop GUI platform developed during the 0.2.0 release candidates
is not part of this repository or this release. It is now developed in
[lukewilliamboswell/roc-gui](https://github.com/lukewilliamboswell/roc-gui).
Applications pinned to a GUI package URL from an earlier release candidate keep
building against that immutable archive but receive no further updates from
here.

## Engine and runtime

Updates do work proportional to the changed set rather than to the graph, row,
or DOM size, and the Wasm command buffer has bounded retention. Scope retirement
releases every node, closure, effect, retained value, and keyed-list
registration it owns. Sequence fuzzers and an allocation-failure campaign
exercise the engine, and their regression corpus runs on every pull request.

## Release artifacts

The release contains the web platform package, `signals-examples.zip` (complete
applications, their native specs, and the matching browser runtime), and
`signals-release.json`. Host binaries and the Linux musl linker inputs are
built in separate attested workflows, admitted by SHA-256 through reviewed
locks, and bundled without rebuilding; the release builds no Zig code. Every
example is built and smoke-tested from the exact archive on Linux and macOS
before one job publishes those tested bytes.
